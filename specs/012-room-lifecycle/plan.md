# Implementation Plan: Room Lifecycle

**Branch**: `012-room-lifecycle` | **Date**: 2026-11-02 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/012-room-lifecycle/spec.md`

## Summary

Extend the existing room catalog so categories and rooms can be edited and moved between active and inactive states without physical deletion. Add room description, numeric-only identification validation, paginated room listing with selectable limit, combined text search, icon-only right-aligned actions, overlay filters, direct category status select, and deterministic suite categories/rooms with valid category relationships in the development seed. The implementation follows the existing contract-first and clean-architecture paths in `packages/.contracts`, `packages/api` and `packages/web`.

## Technical Context

**Language/Version**: TypeScript, Node.js runtime, React

**Primary Dependencies**: Fastify, Zod, Prisma, PostgreSQL, React, TanStack Query, React Hook Form, Tailwind CSS and existing shadcn/Radix UI components

**Storage**: PostgreSQL through Prisma Client

**Testing**: Vitest, API HTTP injection/use-case tests, schema tests and web component/page tests; build validation with Vite

**Target Platform**: Linux server API and browser web application

**Project Type**: Web application monorepo with API, web client and shared contracts

**Performance Goals**: Keep paginated room searches within 2 seconds for 95% of acceptance queries; status/search filters must be applied in the database query and edit operations must remain single-request transactions. The desktop room search control must provide at least 360px of usable width while remaining fluid on smaller viewports.

**Constraints**: Tenant isolation by authenticated `hotel_id`; no physical delete endpoints; numeric identification must match `^\\d+$`; shared contracts precede implementation; all new web controls use shadcn components; the room filter Popover must close on outside click and Escape without shifting page layout; pagination limits are restricted to 25, 50, 100 and 250, with 25 as the minimum and default; all file and symbol names follow the repository snake_case convention where applicable.

**Scale/Scope**: Two aggregates, two paginated lists, two edit flows, room search across three fields, overlay/direct status filters, responsive search sizing, outside-click overlay behavior, one Prisma migration and a deterministic seed of 4 categories and 38 correctly linked rooms.

## Implementation Design

### API and contracts

1. Extend shared `CategoriaQuarto` and `Quarto` types with update payloads; add room `descricao` and `status` to all room representations, plus room list parameters for `pagina`, `limite`, `busca`, `categoria_id` and `status`.
2. Add `status` to the room persistence model and nullable `descricao`; create a Prisma migration with defaults and indexes consistent with existing tenant/category indexes.
3. Add `^\\d+$` to the API room create/update schema and preserve the existing bed uniqueness validation.
4. Add optional room `status` and text `busca` to list query schemas. Validate `limite` against exactly `25 | 50 | 100 | 250`, defaulting to 25, and reset `pagina` to 1 whenever the limit changes. Implement a database `OR` search over room identification, related category name and related bed type; map the web “Todos” choice to an omitted API parameter.
5. Add repository methods for category update and room update, including tenant-scoped lookup, uniqueness handling and transactional bed replacement.
6. Add one use case for each update intent. The use cases validate the target, enforce active-category rules for room writes, and surface not-found/conflict errors.
7. Add `PUT` routes with the same auth, schema and error mapping conventions as existing routes. Do not add delete routes.

### Web

1. Extend API services with update methods and typed list parameters for pagination, limit, search, category and status.
2. Add edit routes/pages for categories and rooms, loading the current resource and submitting through TanStack Query mutations.
3. Reuse `CrudFormLayout`, React Hook Form and existing shadcn controls. The room form adds a shadcn `Textarea` for description and status selection; category and room edit forms expose active/inactive state.
4. Use `usePaginacao`, `SearchBar`, `DataTablePagination` and `ResultCount` for the room list; preserve `pagina`, `limite`, `busca`, `categoria_id` and `status` while changing pages or filters. Configure the limit selector with exactly 25, 50, 100 and 250, defaulting to 25 and resetting the page to 1 when the limit changes.
5. Give the room search input a desktop minimum width of 360px and a fluid width on smaller viewports. Render the search action as a shadcn `Button` with the visible label `Pesquisar` and the search icon. Add a shadcn `Popover`-based “Mais filtros” control only to the room page so the filter content overlays the table context and does not create a layout card; its outside-click and Escape handling must close the overlay without changing the page structure. Keep the category status filter as a direct shadcn `Select` with no `FilterPanel`.
6. Add client Zod validation for numeric-only identification and show the existing toast/form error pattern. Use shadcn `AlertDialog` for inactivation confirmation.
7. Render icon-only edit buttons inside a right-aligned actions column, with accessible labels/tooltips, and retain the no-delete UI contract.

### Seed and verification

1. Extend `clean()` to remove room beds, rooms and categories before removing the hotel.
2. Create categories with the requested names and status `S`.
3. Create room ranges 101–116, 201–216, 302–306 and 301, with deterministic bed configurations and capacities covering the supported types.
4. Create every room with the explicit category ID from its category seed record and verify all 38 relations after seeding.
5. Assign the existing `Quartos` routes to the seeded administrator group and keep the seed output useful for manual verification.
6. Add tests for pagination, combined search, overlay/direct filter behavior, seed relationships and all new schemas/use cases/routes.

## Constitution Check — Post-Design

*Gate after design: PASS.*

- Shared contracts are the first implementation boundary; API schemas derive their types and web services consume the shared types.
- Persistence changes are isolated to Prisma/repositories; route handlers remain limited to HTTP concerns.
- Update and inactivation are explicit use-case intents with tenant-scoped repository operations.
- No physical deletion is reachable from the HTTP API or web UI.
- Numeric validation is duplicated deliberately at both external boundaries and covered by invalid-input tests.
- The design reuses existing shadcn components, adds the missing shadcn Popover primitive if needed, and avoids introducing native select controls.
- The existing repository/use-case seams support unit tests without a database, while route tests use Fastify injection.
